# Migration V001 - Users Table

## Objective
Create base users table with authentication fields, type differentiation, and audit timestamps.

## What Was Created

### Table: `users`
- **id** (UUID, PK): Auto-generated unique identifier
- **email** (VARCHAR(255), UNIQUE): User email address
- **password_hash** (VARCHAR(255)): Bcrypt hashed password
- **user_type** (ENUM): CLIENT, CONSULTANT, ADMIN
- **name** (VARCHAR(255)): Full user name
- **phone** (VARCHAR(20), nullable): Contact phone
- **status** (ENUM): ACTIVE, INACTIVE, SUSPENDED, PENDING_VERIFICATION
- **created_at** (TIMESTAMP): Auto-set on creation
- **updated_at** (TIMESTAMP): Auto-updated by trigger

### ENUMs
- `user_type`: CLIENT | CONSULTANT | ADMIN
- `user_status`: ACTIVE | INACTIVE | SUSPENDED | PENDING_VERIFICATION

### Constraints
- Primary Key on `id`
- Unique on `email`
- Email format validation (regex)
- Phone format validation (E.164)

### Indexes
- `idx_users_email` (email)
- `idx_users_user_type` (user_type)
- `idx_users_status` (status)
- `idx_users_created_at` (created_at)

### Triggers
- `update_users_updated_at`: Auto-updates `updated_at` on row modification

## Design Decisions

### Why UUID for ID?
- Better for distributed systems
- No sequential guessing
- Prevents enumeration attacks

### Why ENUM for user_type?
- Type safety at database level
- Better performance than VARCHAR+CHECK
- Self-documenting schema

### Why Separate user_status?
- Account lifecycle independent of user type
- Supports verification flow (PENDING_VERIFICATION)
- Enables soft suspension without data loss

### Email Validation at DB Level
- Defense in depth (app + DB validation)
- Prevents bad data from any source
- Format: `^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$`
